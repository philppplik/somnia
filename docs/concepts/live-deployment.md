# Live deployment: one-click publish from Somnia over SSH with automatic SSL

Status: proposed concept and design. Not implemented. Needs Philipp's OK on concept and design before any dev work.
Baseline: `int/alpha6` (`622669d`, v12.2.0-alpha.7). Style follows `docs/concepts/studio-shell.md`.

## 1. Goal

A project built in Somnia goes live on the user's own server with one click, under `https://their-domain`, with a valid certificate that renews itself. No terminal, no Docker, no nginx file editing.

Philipp's ask: "intuitive, one-click". He is not a server admin. So:

1. **First time**: a short wizard asks for four things (server address, login, domain, what to publish) and does the rest.
2. **Every time after**: one button, **Publish**. It shows what will change, asks once, uploads, switches over, and tells him the live URL.
3. **When something breaks**: a plain sentence and one button that fixes it or goes back to the last working version. Never a stack trace.

Non-goals: managed hosting by Somnia, CI/CD pipelines, multi-server fleets, databases, Windows servers, Docker orchestration. See section 13.

| Area | Where | Today |
| --- | --- | --- |

| Tauri command surface | `build.rs`, `capabilities/editor.json`, `desktop.rs`, `scripts/errors/gen-commands.mjs`, `check:commands`, `tauriPermissions.test.ts` | Every command is declared in five places and checked by script and test. |

Gap: nothing in the app can reach a remote machine, there is no host identity store, and no "publish target" in the project model.

## 3. Target picture

```
Publish UI (wizard, button, dialogs)        renderer, no secrets, no sockets
        |  CommandSpec  deploy.*            execute level, human confirmation
        v
Deploy service (Rust, desktop.rs side)      SSH/SFTP, TOFU, release layout, health check
        |  SecretBackend (keyring)          SSH key, passphrase, never leaves Rust
        v
User's server (Linux, SSH)                  Caddy (auto SSL), releases/, current symlink
```

Rule: the renderer asks, the Rust side acts. The renderer never sees a key, a passphrase, or a raw socket.

### 3.1 Why these pieces

| Choice | Decision | Reason |
| --- | --- | --- |
| SSH client | Embedded Rust SSH/SFTP library (proposal: `russh` + `russh-sftp`), not the system `ssh` binary | Works the same on macOS, Windows and Linux with nothing installed. We control host-key checking and never shell out with secrets in argv. Exact crate is an open question (section 14). |
| SSL | **Caddy** on the server | ACME (Let's Encrypt) is built in: issues, renews, redirects HTTP to HTTPS, no cron, no certbot hooks. One small config file per site. |
| Releases | Timestamped directories plus a `current` symlink | Atomic switch, instant rollback, no half-uploaded site ever served. |
| Auth | SSH key pair generated by Somnia, public key shown for the server | Layperson-friendly: "paste this once". Password login is only used during first setup if offered, and is never stored. |

## 4. Server model: one root step, then no root ever

Ports 80 and 443 and a system service need root once. After that, nothing Somnia does needs root. Two honest paths:

**Path A, recommended: one-time bootstrap script.**
The wizard produces one copy-paste command block (shown in full before use, with a "what does this do" list). The user runs it once as root or with sudo, in their provider's web console or a normal SSH session. It:

1. Installs Caddy from the distro's official package source, or the static binary if none.
2. Creates an unprivileged user `somnia` (no password, no shell login for others).
3. Installs `somnia`'s authorized key (the public key Somnia generated).
4. Creates `/srv/somnia/<site>/{releases,shared}` owned by `somnia`.
5. Runs Caddy as `somnia` via systemd with only the capability to bind ports 80 and 443 (`AmbientCapabilities=CAP_NET_BIND_SERVICE`). Caddy keeps its certificates in `somnia`'s data directory.
6. Includes `import /srv/somnia/*/Caddyfile` in the main Caddy config, so each site owns its own config file.
7. Node only: enables lingering for `somnia` (`loginctl enable-linger`) so its user services survive logout.

From then on every deploy runs as `somnia`, can write only under `/srv/somnia`, and reloads Caddy through its local admin socket owned by `somnia`. No sudo rule, no setuid, no root SSH.

**Path B, no root at all.** Only if the user truly has no root: Caddy as a plain binary on high ports plus a provider-side redirect, or a DNS challenge (see 8.3). Documented as "advanced", not in the wizard's default path. Many shared hosts give SFTP only: Somnia can still upload (static, no SSL management, host does SSL). Offered as "Upload only" target type.

If a server already runs nginx/Apache on 80/443, the wizard detects the port conflict during the check (6.2) and stops with the message in section 9. Replacing it is never automatic.

Supported servers in v1: Linux with systemd (Debian/Ubuntu first), x86_64 and arm64, reachable by SSH key.

## 5. Release layout and atomic switch

```
/srv/somnia/<site>/
  Caddyfile                 site config, rewritten only by Somnia
  releases/
    20261013T093000Z-ab12cd/   one directory per publish (UTC time + short content hash)
    20261012T180200Z-9f31ee/
  shared/                   user data that survives releases (Node: .env, uploads)
  current -> releases/20261013T093000Z-ab12cd
  .somnia/state.json        last N releases, which one is live, health result
```

Publish steps (the service runs these; each step reports progress to the UI):

1. **Connect and verify host** (section 7).
2. **Preflight**: free disk space, write access, Caddy running, ports, DNS (section 8).
3. **Build locally** the artifact (section 6). Compute file list with hashes.
4. **Diff** against the live release's manifest: added, changed, removed files. This is what the confirmation dialog shows.
5. **Upload** into a new `releases/<id>.partial/`. Unchanged files are hard-linked from the current release on the server (fast, small uploads). Verify hashes after upload.
6. **Rename** `<id>.partial` to `<id>` (atomic within a directory).
7. **Switch**: create `current.new` symlink, then `rename(current.new, current)`. A rename over a symlink is atomic, so requests see either the old or the new site, never a mix.
8. **Node only**: restart the service (6.2), wait for the health check.
9. **Health check**: HTTPS request to the live URL, expect status 2xx/3xx within a timeout. Static: also checks `index.html` hash.
10. **On failure**: switch the symlink back automatically and say so. On success: prune old releases, keep the newest 5 (setting).

Rollback is step 7 pointed at an older release: button **Go back to previous version** in the Publish panel, plus a list of kept releases with date and file count. Rollback is also an `execute` command with confirmation. Database or `shared/` changes are never rolled back, and the UI says so for Node targets.

Interrupted publishes leave only `*.partial` directories. The next publish or a **Clean up** button removes them. They are never served.

## 6. Artifacts: static and Node

### 6.1 Static site (default, the one-click path)

- Source: the project's export output directory (same output as the existing export).
- Server needs only Caddy. Caddy file per site:

```
example.com, www.example.com {
    root * /srv/somnia/example/current
    encode zstd gzip
    file_server
    header { Strict-Transport-Security "max-age=31536000" X-Content-Type-Options nosniff }
    handle_errors { rewrite * /404.html
                    file_server }
}
```

- `www` handling and HTTP to HTTPS redirect come from Caddy defaults. Single-page apps get an opt-in `try_files {path} /index.html`.

### 6.2 Node app (second tier)

- Artifact: a self-contained bundle (built output, `package.json`, lockfile, optional prebuilt `node_modules`). Somnia does not ship a Node runtime. Wizard checks `node --version` on the server against the project's `engines`. If missing: shows the one extra bootstrap line to install it, never installs silently.
- Runs as a **systemd user service** of `somnia` (`somnia-<site>.service`), working directory `/srv/somnia/<site>/current`, env from `shared/.env`, listening on `127.0.0.1:<port>` (port chosen at setup, stored in state).
- Caddy: `reverse_proxy 127.0.0.1:<port>`.
- Dependency install: preferred is uploading a prebuilt bundle for the server's OS and arch. Fallback is `npm ci --omit=dev` on the server inside the new release before the switch. A failed install aborts before the symlink moves.
- Restart: `systemctl --user restart`, then health check. Failure triggers the automatic rollback and a restart of the previous release.
- Secrets for the app (`.env`) are written once through a dedicated "App settings" dialog straight to `shared/.env` with mode 0600. They are not part of the project, the export, or the diff. See section 10.

Out of v1 for Node: workers, cron, multiple processes, zero-downtime socket handoff (a restart gap of a second or two is acceptable and stated).

## 7. Host key: trust on first use with a visible fingerprint

SSH has no certificate authority here, so the first connection must be confirmed by a human.

First connection dialog:

```
Is this really your server?
  Server        203.0.113.10   (example.com)
  Fingerprint   SHA256:Qm7x...Zk4   (ssh-ed25519)
  Words         amber  falcon  river  ...   <- optional easy-to-read form
Compare this with your hosting provider's console or the output of
  ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
[Trust and continue]   [Cancel]
```

Rules:

- Pin the key **per host and port** in an app-owned known-hosts store (not `~/.ssh/known_hosts`, not the project). The fingerprint is not secret, so it may live in app config. Algorithm preference: ed25519, then ecdsa, then rsa-sha2.
- Pinned and matching: connect silently.
- **Changed key**: hard stop, never an "accept anyway" in the same dialog. Message: "This server now identifies itself differently. This can happen after a reinstall, or if someone is intercepting the connection." Shows old and new fingerprint. Buttons: **Cancel** (default) and **I reinstalled the server, replace key**, which needs a second explicit confirmation and a checkbox. Replacement is logged.
- The bootstrap script prints the server's fingerprint at the end. The wizard has a field "Paste the fingerprint printed by the script" so a careful user gets real verification instead of blind TOFU. If it matches, the trust step is skipped.
- The fingerprint shown in every deploy confirmation dialog is the pinned one, so a changed key is visible there too.
- Agents cannot trust, replace, or remove a host key. These are UI-only actions (section 11).

## 8. DNS guidance

DNS is where laypeople get stuck, so the wizard checks it live and explains.

### 8.1 What the wizard shows

```
Point your domain at your server
  Type  Name  Value
  A     @     203.0.113.10
  A     www   203.0.113.10        (or CNAME www -> example.com)
  AAAA  @     2001:db8::10        (only if your server has IPv6)
Status:  example.com  -> 198.51.100.7   not yet your server
[Check again]   [Copy records]
```

- Resolves via DNS-over-HTTPS and the system resolver, compares with the server's public IPs (queried from the server itself).
- Shows per-provider hints as plain text (where the DNS panel usually is). No provider API integration in v1.
- Warns about stale `AAAA` records pointing elsewhere (the most common cause of failed certificates), CNAME at the apex, and `www` missing.
- Propagation: explains that up to a few hours is normal, and offers **Publish anyway, check later**. Caddy retries certificate issuance on its own with backoff, so a site published before DNS is ready becomes HTTPS by itself once DNS arrives.

### 8.2 ACME specifics

- Challenge: HTTP-01 and TLS-ALPN-01 (Caddy default), needs 80 and 443 reachable from the internet. Wizard checks the provider firewall by asking an external reachability probe (open question 14.4) or tells the user which ports to open.
- Let's Encrypt rate limits matter during testing: use the staging CA (`acme_ca` staging) when the wizard's "Test mode" is on, and for all automated tests.
- Wildcards need DNS-01 and a DNS provider token. Not in v1 (token would live on the server).

### 8.3 Raw IP without a domain

Not served over trusted HTTPS in v1. The wizard says so and offers HTTP-only preview with a clear "not secure" label, or asks for a domain.

## 9. UX flow

Entry: a **Publish** button in the top header (next to Project/Export) and a **Publish** panel in the right rail of Code studio (history, rollback). Same commands in the palette.

### 9.1 First-time wizard (5 steps, one screen each, back always possible)

1. **What to publish**: pre-selected from the project (static or Node). One sentence on each.
2. **Your server**: address (IP or name), SSH user (default `root` for the bootstrap, then switches to `somnia`). Button **Create a key for me**. No existing-key import in the happy path (advanced link, uses the vault path).
3. **Prepare the server (once)**: shows the bootstrap block with **Copy**, plus a "What this does" list from section 4. Somnia waits, polling the connection, and advances by itself when the key works. Alternative: "My server is already set up".
4. **Trust the server**: host-key dialog from section 7 (or auto-match with the pasted fingerprint).
5. **Domain**: domain field, live DNS check (section 8), **Publish now**.

Everything entered is saved as a **Publish target** (name, host, port, user, domain, artifact type, pinned fingerprint reference, key reference). Targets live in the project settings, which contain no secrets (section 10).

### 9.2 One-click redeploy

`Publish` with a saved target:

1. Builds, diffs, then shows the confirmation dialog (always, see 11.1):

```
Publish to example.com?
  Server       203.0.113.10:22  as somnia
  Fingerprint  SHA256:Qm7x...Zk4  (pinned 2026-10-13)   [verified]
  Changes      3 changed, 1 new, 0 removed   (12 files, 480 KB to upload)
               ~ index.html   ~ css/site.css   + img/hero.webp ...  [Show full diff]
  Previous version stays available for rollback.
[Publish]  [Cancel]
```

2. Progress line in the status bar plus a detail view: Connecting, Checking, Uploading 7/12, Going live, Checking site. Cancellable until the symlink switch.
3. Result: `Live: https://example.com` with **Open**, **Copy link**, **Undo this publish**.

"One click" therefore means one click to start and one to confirm. The confirmation is deliberate and cannot be turned off for the human or for agents (section 11).

### 9.3 Error states (plain language, one action each)

| State | Message shown | Action offered |
| --- | --- | --- |
| Server unreachable | "Can't reach 203.0.113.10. Check the address and that the server is on." | Retry, Edit target |
| Auth rejected | "The server did not accept Somnia's key." | Show public key and bootstrap again |
| Host key changed | Section 7 | Cancel (default), Replace key (double confirm) |
| Server not prepared | "This server isn't set up for Somnia yet." | Show bootstrap script |
| Port 80/443 in use | "Another web server is already using this server's web ports. Somnia won't replace it." | Show who (process name), Help, Upload-only mode |
| Disk full | "Not enough space: needs 480 MB, 120 MB free." | Remove old releases, Cancel |
| DNS not ready | "example.com doesn't point to your server yet." | Show records, Publish anyway |
| Certificate pending | "Site is live over HTTP. The certificate is still being issued." | Check again; auto-retries, link to cause (DNS, firewall, rate limit) |
| Health check failed | "The new version didn't answer correctly, so Somnia went back to the last version." | Show server log tail (redacted), Retry |
| Node version / install failed | "npm install failed on the server. Nothing was changed." | Show log tail |
| Upload interrupted | "Connection dropped. Nothing went live." | Resume (re-diff and continue), Cancel |
| Rollback failed | "Couldn't switch back automatically." | Show the one-line manual command |
| Key missing from keychain | "The key for this server is gone from this computer." | Create a new key, Bootstrap again |

Rules for messages: no raw SSH output by default, no paths outside `/srv/somnia`, no secrets or key material ever. "Show details" opens a redacted log (section 10.3).

## 10. Security model

### 10.1 Secrets and keys

- The SSH private key and any passphrase live **only in the OS keychain**, through the existing `SecretBackend`/keyring path in `oauth_store.rs` and `desktop.rs`. Slot naming follows the existing service, e.g. `deploy-key:<target-id>`. Key generation (ed25519) happens in Rust; the private key goes straight to the keychain.
- They are never written to project files, `exportState`, `.somnia` settings, logs, error strings, telemetry, crash incidents, or the agent context. The public key is shown to the user and may be stored.
- Renderer gets only status: `{targetId, state, fingerprint?, lastDeploy?}`. Same shape principle as the OAuth `Status`.
- `Debug`/`Display` of key types is redacted. Errors are generic enums, never wrapped lower-level messages that could echo paths or banners with secrets.
- A project file or exported project carries only target metadata (host, port, user, domain, type, key slot id). Opening a shared project on another computer shows "key missing" and the Create-new-key path. Fingerprint pins are per-app, not per-project, so a shared project cannot ship a pre-trusted host.
- Passwords entered for first-time setup are held in memory for one connection and zeroized. Not stored.
- App secrets for Node (`.env`) are not stored locally after upload (the dialog can re-read nothing back). Local storage of them, if wanted later, goes to the keychain only.

### 10.2 Server side

- Dedicated unprivileged `somnia` user, writes only under `/srv/somnia`. SFTP/exec limited to what the service needs (no interactive shell usage by Somnia beyond fixed, parameterised commands).
- All remote commands are built from a fixed allow-list of templates with validated, escaped arguments (site id, release id match `^[a-z0-9-]+$`). No user text is ever concatenated into a command line.
- Path safety: upload paths are normalised relative to the release directory, reject `..`, absolute paths, and symlinks in the artifact. Local file list excludes `.git`, `.env*`, `node_modules` (static), key files, and anything matched by the project's ignore list. The file list in the confirmation dialog is the exact list uploaded.
- Caddy security headers on by default (HSTS, nosniff). HSTS `max-age` starts short in Test mode.

### 10.3 Logging

Deploy log contains step names, timings, counts, release ids, fingerprints, HTTP status. It never contains key material, passphrases, `.env` contents, or command output unfiltered. Server output shown in "details" passes through a redactor (known secret patterns, anything from `shared/.env`). A unit test feeds seeded secrets through every error and log path and asserts they never appear.

### 10.4 Threats considered

| Threat | Mitigation |
| --- | --- |
| Man in the middle on first connect | Visible fingerprint, optional pasted fingerprint from the bootstrap output |
| Server impersonation later | Pinned key, hard stop on change |
| Malicious project or agent triggers a deploy | Execute-level command, UI-only confirmation (section 11) |
| Malicious project file points at an attacker's host | Targets in a project are inert until the user trusts the host in the UI. First use after opening a project always shows the host-key dialog and a "this project wants to publish to X" notice |
| Secret leak through logs/export | Section 10.1 and 10.3, tests in section 12 |
| Path traversal / command injection | Allow-listed templates, path normalisation |
| Stolen laptop | Keys in OS keychain (protected by the OS login), key can be removed from server by deleting one line, the UI explains how |
| Compromised server | Blast radius limited to `/srv/somnia`; no credentials for other systems are stored on it |

## 11. Command surface and the Tauri checklist

### 11.1 CommandSpec

| Command id | Level | Purpose | Confirmation |
| --- | --- | --- | --- |
| `deploy.targets.list` | read | Targets and status (no secrets) | none |
| `deploy.plan` | propose | Build artifact, compute the diff, return the plan (target, fingerprint, file list/diff) | none, no side effect on the server except read-only connect when pinned |
| `deploy.publish` | **execute** | Upload and go live | **Always** the confirmation dialog |
| `deploy.rollback` | **execute** | Switch to an older release | **Always** the confirmation dialog |
| `deploy.target.save` / `delete` | execute | Create or remove a target | dialog in wizard / delete confirm |
| `deploy.hostkey.trust` / `replace` | execute, UI-only | Pin or replace a host key | host-key dialog |
| `deploy.key.create` | execute, UI-only | Generate key into keychain | wizard step |

Hard rules:

- `deploy.publish` and `deploy.rollback` are execute-level `CommandSpec`s whose handler **cannot complete without the confirmation dialog**. The dialog shows the target, the pinned **host-key fingerprint**, and the **file list or diff**, with no "don't ask again".
- The dialog result is a one-time token created by the dialog component inside the renderer's user-gesture path and consumed by the Rust command. The command refuses calls without a fresh token. The token is bound to the plan hash (target, fingerprint, file list), so changing the plan after approval invalidates it.
- **Never UI-free for agents.** An agent may call `deploy.plan` (propose) and may ask for a publish, which opens the same dialog for the human. There is no flag, setting, scheduled job, or MCP route that publishes without a human click. Origin checks in `commandDispatcher` reject `deploy.hostkey.*` and `deploy.key.*` from agent origins (`forbidden-origin`).
- If `allowExecute` is off, the commands are listed but disabled, as for other execute tools.

### 11.2 New Tauri commands: the full checklist

Each new Rust command (planned: `deploy_plan`, `deploy_publish`, `deploy_rollback`, `deploy_target_status`, `deploy_hostkey_pin`, `deploy_key_create`, `deploy_bootstrap_script`, `deploy_dns_check`) must have all of:

1. `build.rs`: command name added to the app manifest command list.
2. `capabilities/editor.json`: permission entry for the command.
3. `desktop.rs`: registered in `invoke_handler`.
4. `scripts/errors/gen-commands.mjs`: command known to the generator, so error-code mapping is generated.
5. `pnpm check:commands` (`gen-commands.mjs --check`) passes in the same change.
6. `tauriPermissions.test.ts`: test updated so capability, `build.rs` and handler lists agree.

No command is merged with any of the six missing. Streaming progress uses events, which are declared the same way as existing events.

Secrets rule for commands: parameters and results never contain key material. The target is identified by id.

## 12. Test strategy

No real server is ever touched in tests. In particular Philipp's vServer is out of scope for all automated and manual development testing. Any test against real hardware is a separate, explicit, later decision by Philipp.

| Layer | What | How |
| --- | --- | --- |
| Unit (Rust) | Release id, diff, path normalisation, command templates, host-key store, TOFU state machine, redactor, state machine of a publish | Pure logic behind traits (`SshTransport`, `SecretBackend`, `Clock`). Same pattern as `oauth_store.rs` |
| Mock SSH (Rust) | Every error state in section 9.3, interrupted upload, host key change, auth failure, slow disk, rollback failure | In-process fake `SshTransport` with scripted responses and an in-memory filesystem. Fast, runs in every CI job |
| Container integration | Real SSH and SFTP, real symlink atomicity, real Caddy, real systemd user service for Node | Disposable container (OpenSSH + Caddy + minimal systemd or a supervisor shim) started by the test, random port, throwaway host key and keypair. Caddy uses its **internal CA / ACME staging** against a local test ACME server (for example Pebble) so no Let's Encrypt traffic and no rate limits |
| Atomicity check | During a publish, a loop fetches the site and asserts each response is entirely old or entirely new | Container test with concurrent requests |
| Security tests | Seeded secrets never appear in logs, errors, `exportState`, project files, IPC payloads | Property-style tests over all error paths |
| Tauri contract | Checklist 11.2 | `tauriPermissions.test.ts`, `check:commands` |
| UI | Wizard steps, dialogs (host key, confirm, changed key), error messages, i18n parity en/de/es/fr/pt-BR, a11y of dialogs | vitest + Playwright against the mock transport |
| Agent safety | An agent origin cannot publish without the dialog, cannot trust a host key | Dispatcher tests for each command id |

CI: runs wherever the existing checks run locally or in the existing pipeline. Container tests are a separate script (`test:deploy-container`) that needs a container runtime, and are skipped with a clear message when none is present. This concept adds no GitHub Actions usage.

Manual acceptance (later, by Philipp's decision only): a throwaway VM, never the vServer.

## 13. Milestones

Each is shippable and gated by `tsc`, `vitest`, `check:commands`, i18n parity.

1. **Foundations, no UI**: `SshTransport` trait, mock transport, release layout and diff logic, host-key store, redactor, key creation into the keychain. Unit and mock tests.
2. **Real transport + container tests**: embedded SSH/SFTP implementation, container harness with Caddy and a test ACME server. Atomic switch and rollback proven.
3. **Commands and guard rails**: `CommandSpec`s, confirmation token, full Tauri checklist, agent-origin tests. Still no wizard.
4. **Publish panel and dialogs**: target model, confirmation dialog with fingerprint and diff, progress, results, rollback list. Works with a manually prepared server.
5. **First-time wizard**: key creation, bootstrap script, host-key step, DNS check, "Test mode" with staging CA.
6. **Static polish**: SPA option, headers, www handling, upload-only target, cleanup of partial releases.
7. **Node tier**: runtime check, systemd user service, `.env` dialog, health check and automatic rollback.
8. i18n, docs, screenshot baselines.

Steps 1 to 5 deliver Philipp's one-click wish for static sites. Step 7 is optional and can wait.

## 15. Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Port conflict with existing web server | Wizard dead end | Detect early, stop, offer upload-only, never replace |
| Let's Encrypt rate limits during development | Blocked certificates | Staging CA and local ACME server in all tests, Test mode in wizard |
| Wrong DNS (stale AAAA) | Certificate never issues | Live DNS check, explicit AAAA warning |
| New SSH dependency surface | Supply-chain and maintenance | Pin exact version like `keyring =3.6.3`, small wrapper trait, review before adding |
| Layperson confusion at bootstrap | Abandoned setup | Copy-paste block, auto-detect when done, plain "what this does" |
| Accidental leak of key or `.env` | Critical | Section 10, seeded-secret tests, no secrets in project files |
| Host-key prompt habituation | Weak TOFU | Pasted-fingerprint path, hard stop on change, fingerprint in every confirmation |
| Node app restarts drop requests | Short outage | Stated in UI, health check and rollback, socket handoff later |
| Scope creep to a hosting product | Late delivery | Section 1 non-goals |

## 16. Out of scope

No Somnia-hosted infrastructure, no Docker or Kubernetes, no database provisioning or migration, no wildcard certificates, no DNS provider API, no Windows server targets, no multi-server or blue/green setups, no change to Live View, studio switching or the agent panel, no code changes in this document's change.
